# Retrieval

`app/storage/search.py` runs independent exact pgvector and Postgres full-text candidate searches against the selected private local index. `app/storage/retrieval.py` adds deterministic rank fusion, separate published-card search, and bounded reads of stored original passages. Hits preserve document/run/hash/chunk identity and exact source locations. The answer loop and CLI pass local tests and a disposable database proof with synthetic provider responses. A live pilot and human review exposed answer quality failures; an externally exposed API remains unbuilt.

```mermaid
flowchart LR
    Q[User question] --> V[Vector search over versioned chunk embeddings]
    Q --> T[Postgres full-text search over chunk text]
    V --> R[RRF combines ranked lists]
    T --> R
    R --> E[Agent reads candidate source spans]
    Q --> C[Separate evidence-card search when useful]
    C --> E
    E --> A[Answer with source citations, or say evidence is insufficient]
```

Vector search uses the selected embedding specification, whose payload must match its content-derived ID, dimensions, metric, and chunking version. Before private query embedding, the current endpoint must qualify for ZDR, denied data collection, a pinned provider without fallback, and the price ceiling, including any model-specific route override. Queries use the spec's `search_query` input type where specified.

Full-text search uses `simple` lexemes, `websearch_to_tsquery`, a GIN index, and `ts_rank`; whole-question searches with no all-term hits retry as an OR query over their words. Both channels filter through the selected active profile and run before limiting, with stable chunk-ID ties. RRF sums `1/(60+rank)` over at most 20 hits per channel and returns at most 20 candidates, deduplicating identical source-span sets. Raw channel scores are not combined. Explicit historical selection remains available only through the underlying evaluation search functions.

Card search uses FTS over statement, situation, action, result, and principle, separately from RRF. An all-term query with zero hits retries a bounded OR query; the trace records the mode. Only ready card artifacts named in the active publication are eligible, and repeated exact evidence spans are deduplicated. Card hits carry their chunk's spans so the agent can read the whole chunk, and `chunk_cards` returns the selected cards of discovered chunks in source order. Card fields are discovery context, never citation evidence. Document-scoped find searches original indexed chunks in the exact active document revision of a discovered reference. Stored-source reads validate document/run/hash/chunk identity and allow at most 2,400 characters at a validated offset within one selected span. A continuation reports its next offset and gets a distinct citation ID; reads cannot cross non-whitespace excluded source gaps or stale revisions. The caller owns a read-only repeatable-read transaction. The earlier three local card probes verified 30 original reads and measured SQL execution around 14–16 ms; the new fallback and find SQL pass isolated local database tests.

The selected six-file profile uses structural/raw chunks, `perplexity/pplx-embed-v1-0.6b`, 1,024 dimensions, cosine distance, and `raw-v1`, with 83 vectors and 510 validated cards. The active-profile trial scores all 37 checked questions; 31 supported questions require 51 spans. Negative questions have no recall score and remain visible in the report.

| Exact vector | 41/51 | 44/51 | 47/51 |
| Full text | 28/51 | 40/51 | 44/51 |

RRF does not improve these aggregate results; it has lower coverage at K=5. At K=20 its four missing spans belong to `tim_conversion_recommendations` and `tim_message_testing`. These are candidate-recall diagnostics, not answer-quality scores. The earlier live answer pilot found that the agent often stopped after inspecting too few relevant passages; the current harness reads whole chunks and checks a finish against unread chunks of sources already used. Exact vector ordering remains the correctness baseline; HNSW waits for representative recall and query-plan checks.

`python -m evals.retrieval_trial --provider-tag perplexity/int8 --max-usd 0.01 --report .local/retrieval-dry-run.json` checks labels against stored source revisions without vault access or model calls. Set `KNOWLEDGE_DATABASE_URL`; add `--live` with `OPENROUTER_API_KEY` for one route-gated query-embedding batch. Reports must be new files under ignored `.local/`. ## Local answer core

`app/agent/harness.py` controls strictly parsed version-2 `search`, `search_cards`, `find`, `read`, and `finish` JSON actions through `ModelClient`. Each invocation owns its limits, candidates, inspected evidence, and question-derived investigation needs; source content cannot modify host tool budgets. Before the first model turn the host runs one hybrid search with the question and records it as `host_search`. Candidates are one per chunk, keep their best rank across searches, and are shown unread-first by rank (20, plus the two best of any source those leave out) with a 200-character preview and up to five facts from the selected cards made from that chunk. One `read` inspects every span of the chunk, including continuations past 2,400 characters; each passage keeps its own citation ID such as `E3.1` or `E3.1@2400`, so citations stay span-level. A card-search hit becomes a candidate for its whole chunk.

The host ignores fields that do not belong to the chosen action, accepts a passage ID such as `E6.5` as chunk `E6`, and returns the specific validation rule on a rejection. It retains a valid search or read if the model also emits draft-answer fields, requires a read after two discovery actions while unread candidates remain, and rejects a repeated query with the leads that query already produced. A voluntary finish with an open material need gets one correction opportunity. A voluntary finish is also checked, at most twice and only after new reading, against unread chunks from sources already used; a repeat finish without new reading is accepted. Complete answers require inspected inline citations; fabricated, unread, or mismatched citation lists are rejected. This verifies provenance, not whether every claim is semantically supported. A later malformed JSON response receives bounded correction feedback using the existing inspected evidence; an invalid first response, truncation, route failure, or exhausted allowance remains an explicit failure. Malformed output is retained only when a private report was explicitly requested.

Prompt version `answer_agent_v11` describes these tools, asks for short queries, requires speaker-aware attribution (an interviewer's question and a reader's "My note" are not the author's statement), and asks for every distinct relevant point in inspected passages on broad questions. Request/input budget, deadline, and model-mismatch failures have safe categorical stop reasons. With remaining allowances close to exhaustion, the host hides candidates and restricts the schema to `finish`, keeping inspected originals available for synthesis and recording the finalization trigger. The time reserve accounts for recent request latency. The default serialized-input allowance is 800,000 bytes; the finite `broad` CLI profile (20 model calls, ten chunk reads, 420 seconds, 1,600,000 bytes) permits more investigation and synthesis with a separately checked worst-case spending bound.

The result includes cited passages, the full inspected ledger, retrieval ranks and provenance, gap/sufficiency decisions, stop reason, and elapsed time. Failed tools and exhausted budgets preserve the prior evidence. The model adapter accepts optional OpenAI reasoning effort without changing ingestion defaults and rejects truncated structured responses. Answer HTTP calls share a deadline and use a conservative serialized-input allowance for their spending bound.

`python -m app.agent.cli` calls the same stateless core inside a read-only repeatable-read transaction. It preflights pinned embedding and structured generation endpoints, reports usage/cost, and writes private traces only to explicitly requested new `.local/` files. Consecutive CLI requests start with fresh clients and ledgers. See [README.md](README.md#ask-a-question) for commands. The original version-3 rubric and prompt-v6 pilot remain unchanged, and 21 submitted human review entries are preserved with exact answer identities and a checksum under ignored `.local/`. Version-4 has 91 checks and 59 exact source-block alternatives verified against six source revisions; its criteria await user review before freeze. The grader core verifies inspected bytes against the originals and exact grounding citations, but is uncalibrated. Under prompts v9 and v10 the live Q1/Q2/Q8/Q4 checks on selected `v5` cards found missing essential facets, sentence-sized source reads, generic advice, and invented hiring steps; in those runs the agent never called card search, each read returned one span, and only the last 16 candidates were visible. Under prompt v11 and the harness above, at GPT-5 mini medium reasoning, the final run (`.local/stage5-v11-d/`) completed all four: Q1 read ten chunks, Q2 five, Q8 five across both authors, and Q4 the one relevant note, for $0.24 measured. By agent review against rubric v3, Q2, Q4, and Q8 cover their essential facets, while Q1 omits two facets stated in a chunk it read and Q1 and Q8 close with material the prompt forbids. Runs vary: an earlier v11 run of Q1 stopped after three chunks before the same-source finish check existed. The `v8` and `v9` card candidates failed source factuality, so `v5` remains selected and no matched card-answer comparison was run. `--no-cards` withholds card facts and card search; `python -m evals.card_value` compares two such arms. In that test (`.local/stage5-u9-decision.json`) cards changed nothing on five narrow questions and gave a modest, consistent gain in chunks read and facets covered on Q1, Q3, and Q8, for roughly 60-70% more cost. The user has since decided to remove evidence cards, so card search, card facts, and the switch described here are due to be deleted. No semantic quality baseline has been formally accepted; the user judged the v11 answers very good informally; the [current plan](docs/plans/2026-10-02-001-refactor-remove-cards-finish-answer-gate-plan.md) governs the remaining rubric, grader, repair, and final gate work.
