# What should sit beside chunk retrieval? Research for the answer agent

Date: 2026-10-02. Scope: web research only, with no code changes. Every factual claim has a link. Where a claim is my own reasoning, it is marked **[reasoning]**.

## 1. Verdict

**Our failure is mainly a reading and coverage problem, not a finding problem.** Vector search alone finds 47 of 51 required passages at K=20. The agent then fails to read the chunks that hold some required points. The evidence below favours tools that put more of the right source in front of the model and that split a broad question into parts. It does not favour another LLM-written index layer. **[reasoning, based on our own numbers]**

**Approach 1, which the evidence supports best: let the agent read whole sources or whole sections, with an outline tool.** When a search hit falls inside a long transcript, the agent should be able to open that source's outline. It should then read contiguous sections, or the whole file if the file is small enough.
- Anthropic says that a knowledge base under about 200,000 tokens can simply go into the prompt, with no RAG ([Anthropic, Sep 2024](https://www.anthropic.com/engineering/contextual-retrieval)). Our pilot is about 84 × ~800 ≈ 67k tokens **[reasoning, estimate]**.
- With enough resources, long context beat RAG on average in an EMNLP 2024 study, while RAG stayed much cheaper ([Li et al., 2024](https://arxiv.org/abs/2407.16833)).
- Claude Code dropped its vector index for model-driven glob, grep and read. Its team says this "beat everything" they tried, including "recursive model-based indexing" ([Pragmatic Engineer, Mar 2026](https://newsletter.pragmaticengineer.com/p/building-claude-code-with-boris-cherny)). Anthropic recommends "just in time" loading through lightweight identifiers, combined with some upfront retrieval ([Anthropic, Sep 2025](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).
- The limits are real. Accuracy falls as the input grows. Focused ~300-token prompts beat full ~113k-token prompts on LongMemEval for every model family tested ([Chroma, Jul 2025](https://www.trychroma.com/research/context-rot)). Most models degrade past 32k–64k tokens in RAG settings ([Databricks, Nov 2024](https://arxiv.org/abs/2411.03538)). Weaker models gain more from RAG than from long context ([LaRA, ICML 2025](https://arxiv.org/abs/2502.09977)). GPT-5 mini is a small model, so this must be tested, not assumed.

**Approach 2, the second-best supported: break the question into sub-questions on the host side and search for each one.** This targets cross-source questions and broad questions. Commercial answer engines missed about 50% of core sub-questions. Using core sub-questions in retrieval and generation gave a 74% win rate over the same system without them ([Xie et al., NAACL 2025](https://aclanthology.org/2025.naacl-long.301/)). Anthropic's research agent splits work across parallel searches. Token use alone explained 80% of the variance in performance ([Anthropic, Jun 2025](https://www.anthropic.com/engineering/multi-agent-research-system)). The host should fan out the searches. The small model should not be trusted to do it: the model almost never uses our card search tool today.

**Cheap optional add-on: a reranker over a wider set of candidates.** It is well measured. Databricks reports recall@10 rising from 74% to 89% on its benchmarks ([Aug 2025](https://www.databricks.com/blog/reranking-mosaic-ai-vector-search-faster-smarter-retrieval-rag-agents)). Anthropic reports a 67% cut in top-20 failures when reranking is combined with contextual retrieval ([Sep 2024](https://www.anthropic.com/engineering/contextual-retrieval)). But our top-20 recall is already about 92%. Rerankers can also get worse when they score too many documents ([Jacob et al., SIGIR workshop 2025](https://arxiv.org/abs/2411.11767)). Use it only if the experiments show that ranking order decides what the agent reads.

**Avoid for now:**
- **Full GraphRAG or LightRAG.** Indexing costs about 1,000 times as much as a vector index ([Microsoft, Nov 2024](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)). Under neutral evaluation, LightRAG's reported win over plain RAG reversed ([Zeng et al., 2025](https://arxiv.org/html/2506.06331v2)). On standard QA, GraphRAG, RAPTOR and HippoRAG scored below a plain strong dense retriever ([HippoRAG 2, 2025](https://arxiv.org/html/2502.14802v2)).
- **An LLM-maintained wiki as an answer source, for now.** It has no published measurements. Karpathy's own note admits that errors compound and that the wiki needs regular checking passes ([gist, Apr 2026](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)).
- **More per-passage cards or propositions.** See the next point.

**Are per-passage cards or propositions supported?** Weakly, and not for our case. Proposition indexing helped unsupervised retrievers a lot (Recall@5 up 22–35%). It helped supervised retrievers only a little (up 2–4.5%) ([Dense X, EMNLP 2024](https://aclanthology.org/2024.emnlp-main.845.pdf)). Our embedder is a modern supervised model. HippoRAG 2 names "LLM-generated noise" in an expanded corpus as the reason structure-adding methods lose on simple QA ([2025](https://arxiv.org/html/2502.14802v2)). RAPTOR's own audit found hallucinations in 4% of summary nodes ([RAPTOR, 2024](https://arxiv.org/html/2401.18059)). That is close to the ~5% error rate we measured in our richer cards. Our own result of no effect on narrow questions and +70% cost matches this literature **[reasoning]**. A "description beside the chunk" does help a little with choosing what to read. The tools in Approach 1, an outline plus section titles, cover the same need without new LLM-written facts **[reasoning]**.

**What I am unsure about:**
1. Whether GPT-5 mini handles 20–60k tokens of transcript well. No source tests that model.
2. Whether the recurring-themes, "find all" and contradiction questions in type (d) will need a global index later. GraphRAG-style community summaries are the only measured option for corpus-wide questions ([Edge et al., 2024](https://arxiv.org/html/2404.16130v2)). LazyGraphRAG is the cheap form. It is still too early to build either.
3. Almost no published evidence is about single-user personal vaults. Most evidence comes from enterprise search, coding agents or academic benchmarks.

## 3. Case studies

1. **Anthropic, Claude Code (2025–2026).** They built early versions on RAG with a local vector database. They tried local vector databases and "recursive model-based indexing". Plain model-driven glob and grep "beat everything". The reasons were stale indexes, permission complexity and quality. No numbers are published. [Pragmatic Engineer, Mar 2026](https://newsletter.pragmaticengineer.com/p/building-claude-code-with-boris-cherny)
2. **Cursor (Nov 2025).** They kept grep and added their own trained embedding model for semantic search. Offline, accuracy was 12.5% higher (6.5–23.5% by model). Online A/B: code retention +0.3% overall and +2.6% in codebases with 1,000+ files. Their conclusion: the combination is best. This is a counterweight to "grep is all you need". [Cursor](https://cursor.com/blog/semsearch)
3. **Anthropic multi-agent research (Jun 2025).** They built parallel subagents for broad research. The system beat a single agent by 90.2% on an internal evaluation. It used about 15× the tokens of chat. They started evaluating with about 20 queries and an LLM judge rubric that includes completeness. They note that agents take different valid paths on the same input. [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
4. **Microsoft GraphRAG, then LazyGraphRAG (2024).** GraphRAG beat vector RAG on comprehensiveness (72–83% win rates) for global questions over about 1M tokens of podcast transcripts. Indexing was expensive. Microsoft then built LazyGraphRAG, with indexing cost equal to vector RAG and 700× lower query cost at similar quality. All results come from LLM-judged pairwise comparisons. [GraphRAG paper](https://arxiv.org/html/2404.16130v2), [LazyGraphRAG](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)
5. **Unbiased GraphRAG evaluation (2025, revised 2026).** The authors re-ran published GraphRAG comparisons with position, length and trial bias controlled. LightRAG's 66.7% win rate over naive RAG fell to 39.06%. Other gains were below 10% win rate. Lesson for us: LLM-judge comparisons need order swaps and repeat runs. [Zeng et al.](https://arxiv.org/html/2506.06331v2)
6. **HippoRAG 2 (OSU, 2025).** This is a negative result for structure layers. RAPTOR, GraphRAG and HippoRAG v1 all scored below a plain NV-Embed-v2 retriever on NQ, multi-hop QA and NarrativeQA. For example, NarrativeQA F1 was 25.7 for the dense retriever, 21.4 for RAPTOR and 23.0 for GraphRAG. The authors blame LLM-generated noise added to the corpus. [HippoRAG 2](https://arxiv.org/html/2502.14802v2)
7. **LinkedIn customer service KG (SIGIR 2024).** They built a graph of tickets as trees, with clone links and similarity links. MRR rose from 0.522 to 0.927. Median resolution time fell 28.6% over about 6 months in production. It works because tickets already have fields and links. Our transcripts do not. [LinkedIn](https://arxiv.org/html/2404.17723v1)
8. **Dropbox Dash (Nov 2025).** They found that more tools meant "slower, less accurate decision making". They consolidated retrieval into one tool over one index and used a knowledge graph only for ranking. No numbers are published. [Dropbox](https://dropbox.tech/machine-learning/how-dash-uses-context-engineering-for-smarter-ai)
9. **Sourcegraph Cody (Feb 2024, older).** They dropped embeddings for search-based context, citing upkeep, privacy and scale. [Sourcegraph](https://sourcegraph.com/blog/how-cody-understands-your-codebase)
10. **Databricks long-context RAG study (Nov 2024).** It tested 20 models with 2k–2M tokens of retrieved context. Only a few frontier models stayed accurate above 64k. Failure modes differed by model. [Databricks](https://arxiv.org/abs/2411.03538)

## 4. Smallest experiments for the top two approaches

Use the 8 pilot questions and the 6 files. Run **5 runs per arm**. Three runs is too few to see run-to-run variance. Report the mean and the worst-of-5, in the spirit of pass^k: "all k runs succeed" ([τ-bench, Sierra 2024](https://sierra.ai/blog/tau-bench-shaping-development-evaluation-agents)). Keep the citation check unchanged. Score required-point coverage with our existing labels, not with pairwise LLM win rates (see case 5).

**Step 0: ceiling check (one day). This decides everything else.** Arm "all-in-context": put all 6 files (about 67k tokens, to be confirmed) into the prompt with GPT-5 mini. Keep the citation rule. No search.
- If broad-question coverage is not clearly better than baseline, the limit is the model's synthesis, not retrieval. In that case no retrieval add-on, including cards, graph or wiki, will fix it. Look at the model or the answer step instead. **[reasoning]**
- If coverage is clearly better, retrieval and reading are the bottleneck. Go to Experiment A.

**Experiment A: whole-source and outline reads.** Add two tools. `outline(source)` returns headings or timestamped section titles taken from the source itself, with no LLM text. `read_section(source, range)` returns contiguous text, or the whole source if it is under a set token cap, for example 30k. Arms: baseline (no cards), cards (current), outline+read (no cards).
- Success: on broad and cross-source questions, mean required-point coverage is at least 15 points above baseline and at least equal to cards. Worst-of-5 is also better than baseline. Narrow questions show no loss. Cost per question is no more than the cards arm.
- Failure: coverage within noise of baseline, or a gain only with cost above 2× baseline.

**Experiment B: host-side decomposition.** Before the first search, one GPT-5 mini call writes 3–5 sub-queries. The host runs each one, plus the original question, through the existing hybrid search. It shows the union grouped by source, with the top 2–3 per sub-query guaranteed a slot. Run it with and without Experiment A's tools.
- Success: the cross-author question passes in 5 of 5 runs, and broad-question coverage improves by at least 10 points over baseline.
- Failure: no change in coverage, or more variance.

If both succeed, A plus B together is the candidate design. Remove cards if A matches them. Try a reranker only if logs show required chunks retrieved but ranked too low to be read.
