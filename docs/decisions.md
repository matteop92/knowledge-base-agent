# Decisions

The choices that shaped the project, and why. Each one was made against a measurement where one was possible. The numbers are in [evaluation.md](evaluation.md).

## Principles

1. **Original files are the authority.** Source files are never changed. Anything generated can help find a passage but never replaces the passage as evidence.
2. **Provenance is continuous.** Every stored item resolves to a document ID, the hash of the source it was made from, and an exact span of text. A re-upload replaces the active view only after the new run succeeds.
3. **Search uses two signals.** Embeddings and keyword search run independently and are merged by rank, because their scores cannot be compared directly.
4. **The agent can investigate, within limits the application owns.** It may rephrase, search again and read neighbouring material. Budgets for calls, bytes and time are set by the host, and source text cannot change them.
5. **Models are replaceable.** The application talks to a thin `ModelClient` interface. Today the adapter is OpenRouter, pinned to providers that do not retain or collect data. Every role could be filled by an open-weight model.
6. **Behaviour is inspectable.** Prompts, chunk boundaries, retrieval ranks, tool calls and citation decisions are recorded in receipts that can be reviewed later.
7. **Keep it small.** Python, FastAPI, Postgres with pgvector and full-text search, an explicit agent loop in code, and a plain web app. No graph database, queue or multi-agent framework.

## Decisions and their evidence

| Decision | Why |
| --- | --- |
| **Structural chunks of the raw text** (600 to 1,000 tokens). | On six real files, structural chunks found 47 of 51 required passages in the top 20, against 45 for fixed 800-token chunks. Adding a model-written context sentence to each chunk lost one of those, so it was dropped. |
| **No evidence cards, no summaries in the index.** | A card restated a sentence already in an embedded chunk, gave a small gain on broad questions and cost about 70% more per question. Section and document summaries failed a source-grounding review (one joined two separate highlights into a single cause). Both were removed. |
| **Postgres full-text search, not BM25.** | It is the simple baseline. A true BM25 service would be another piece of infrastructure, justified only by measured need. Merged ranking did not beat vector search alone on the test set, so no more search machinery was added. |
| **Exact vector search, no approximate index yet.** | The corpus is small. An approximate index waits for measured recall and query plans on a larger one. |
| **The host runs the first search; the agent reads whole chunks.** | An early pilot showed the agent stopping after too few relevant passages. Reading whole chunks and checking a finish against unread chunks of sources already used fixed that. |
| **The web app reads the six best chunks before the first model turn and does not send a finish back for unread chunks.** | Turns that only chose a chunk to read took 33% of answer time, and finishes sent back took 40%. With both changes the median answer went from 114 s to 37 s and p95 from 280 s to 92 s, at 1.7 model calls instead of 5.5. The graded score moved from 89.3% to 88.9%, within the grader's noise. Reading ten chunks instead of six was slower and scored lower (87.7%). **Fallback if answers feel incomplete:** set `coverage_checks = 1` in `AnswerSettings` (`app/api/settings.py`). That allows one send-back: 48 s median and 106 s p95, $0.013 per answer, 90.2% graded. |
| **Every question is routed to catalog, narrowed or plain by one Jev call.** | The luna property router only separated count and list questions, ran on first questions only, and answered yes or no: "what's the latest note I've uploaded" listed all seven notes in path order, and it could not send a question to the normal loop with fewer sources. On 67 labelled questions Jev 1.14 routed 66 correctly with no plain question sent to the catalog (luna: 63, with 3 plain questions sent to the catalog), built every catalog plan correctly on 9 unseen phrasings, and took 0.27 s at the median against 1.6 s, for $0.007 per 201 calls. It runs through OpenRouter's `/api/v1/systemone` with zero data retention; `gpt-6-luna-decisions` has no zero-retention route and stays a later option. "Plain" is listed first and narrowed and catalog each need 0.6 probability, so a doubtful question takes today's path. |
| **Catalog questions are a typed plan applied in Python, never SQL from a model.** | The router already loads every source, so one copy of the label rules filters, sorts and counts that list. A small documented schema avoids text-to-SQL column-matching errors and keeps the database surface closed. Move to SQL if the vault reaches many thousands of notes. |
| **A source's type is its own `type` or `source_type` property, else its folder, else the classifier's guess.** | The classifier called 13 of 25 notes in the Notes folder a transcript, social post, book or article, so "how many transcripts" counted notes that were quotes or passages. The folder is where the person filed it; a note that really is a full transcript goes in Transcripts or sets `type: transcript`. Only a folder with no type (none today) falls back to the classifier. |
| **A narrowed question searches only sources picked by type, folder, period or "newest", never by person or tag.** | "What would Tim Ferriss recommend" must still find his words on other people's podcasts. "Summarise my latest note" is narrowed (newest by added date); "which note did I add last" is a catalog question. Code reads dates and numbers because the model reads them poorly. |
| **A source's added date is when it first entered the index.** | The earliest load or capture job. The first bulk load (finished by 2026-10-18 10:18 UTC) says nothing about when a note was added, so those notes take their own created date, and the answer says when that was used. |
| **Transcript passages carry their speaker, and a wrong attribution is flagged, not rewritten.** | The saved answer "Tim notes that some platforms (he cites X)" cited a passage spoken by Niels Hoven. Speakers come from the parsed blocks at read time, so nothing is re-embedded. The runtime check flags a sentence that names a speaker of a cited transcript when none of the named speakers spoke a passage it cites; the eval check is stricter: a sentence citing a guest's passage fails if it names the host instead (a sentence that names nobody passes). Auto-repair waits until the hit rate is known. |
| **The speaker is also written into the passage text; the speaker rule stays opt-in.** | Writing `Niels Hoven:` at the start of the passage raised the Tim Ferriss eval on v13 from 1 of 6 to 3 of 5 with no extra call (2 of the 3 passes cited a guest passage and named it correctly). The rule on top (v15) also scored 3 of 5, but none of those passes cited a guest passage, and it lost coverage on the 85-check list (90.6% against 97.2%), so v13 and v14 stay the defaults. A one-time retry on a flagged answer reaches 4 of 5 but adds about 40 s, so it is off. |
| **"Which was added first or last" is its own router question.** | Rewording the route options to cover it weakened plain count questions. A yes at 0.9 or more, with the narrowed and catalog routes together at 0.6, makes the route catalog. |
| **The answer model stays `gpt-5-mini` at medium reasoning.** | Medium beat low and minimal in an earlier test. `gpt-6-luna` as the answer model had a better median but a worse p95 (150 s against 128 s on the trial subset), so it was dropped. |
| **Answer quality is rated by a person against a frozen 85-check list.** | A model grader was built and calibrated on held-out answers, but it missed the pass bar. It now pre-rates answers and a person confirms. See [evaluation.md](evaluation.md). |
| **Prompt v13 is the answer baseline.** | It replaced "cover every point in the passages read" with a relevance test, cutting points outside the question's scope from 9 to 3 with a similar overall score. |
| **The hosted database schema is private.** | The `knowledge` schema is outside the exposed API, `anon` and `authenticated` get no grants, and the app logs in as a separate narrow role. |
| **The server's style rule allows inline styles (`style-src 'self' 'unsafe-inline'`); scripts stay `'self'` only.** | Mermaid draws its diagrams with a `<style>` element and inline style attributes, which `style-src 'self'` blocks. A sandboxed diagram page would keep the strict rule but needs its own route, a frame exception and iframe sizing. The app draws all text as elements and never as HTML, so injected styling is a low risk. |
| **Card facts (type, platform, source name, people) are derived when the Sources page loads and never written back.** | The vault is the authority and the sync is two-way, so the app must not edit notes to add fields. Platform is the note's `platform` field, else the source URL host, else left out; nothing is guessed. |
| **"Ask about this" skips the question router and never widens.** | The user already chose the scope, so a router call would add cost and could pick a different one. The scope is sent with each follow-up while its chip shows, and a scoped search that finds nothing says so instead of searching everything. |
| **Phone filters are a summary plus one searchable page per long list.** | People and tags run to hundreds. One sheet of pills or rows would scroll for minutes, so a facet with many values gets its own page with a search box, chosen items pinned on top, the most-used first, then A to Z with a letter rail. Date and type are short and stay on the summary. |
| **Capture creates new files only.** | The server never edits or overwrites a note. A file in the vault is changed only by its owner. Capture is refused unless the server's vault sync is two-way. |
| **Spend is capped everywhere.** | Live model calls need an explicit flag and a dollar ceiling. A daily cap applies to all spending, and a ledger records measured cost. |
| **Schema changes are versioned SQL.** | Migrations live in `supabase/migrations/` and deploy through Supabase's GitHub integration when merged into `main`. |

## Later work, not built

- **Connections across sources.** Search finds what matches the question's words. It does not surface a related idea in another source. Candidates are related-chunk links from the existing embeddings and a small theme layer, and they should be tried only after the evaluation includes cross-source and whole-vault questions.
- **Questions about the whole vault.** "Find all" and recurring-theme questions need more passages than a top-20 search returns.
- **Showing progress while an answer runs.** Answers are faster (about 37 s median), but the final finish is still one 15 to 38 s model call. Streaming does not shorten a JSON action; showing which sources are being read would make the wait easier.
